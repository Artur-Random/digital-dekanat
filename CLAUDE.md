# digital-dekanat

Рабочий прототип личного кабинета студента «Кабинет, который предупреждает заранее» для номинации «Вайб-кодинг» конкурса MGIMO AI Challenge 2026. Вуз-основа: МГПУ, Институт психологии и комплексной реабилитации (ИПКР).

Это концепт для конкурса, а не официальный сервис МГПУ. Отправка работы: до 22.11.2026 23:59 МСК. Сайт должен работать до 28.11.2026.

## Источники правды

Перед любой задачей прочитай:

- `docs/spec-v1.md`: экраны (S0–S9 студент, E1–E4 сотрудник), сценарии, модель данных, тестовые аккаунты, план.
- `docs/norms-registry.md`: реестр норм с кодами N-xx. Единственный источник правил вуза.

Если задача противоречит спецификации или реестру, остановись и спроси. Не меняй стек, структуру папок и модель данных без явного согласования: предложи изменение и жди ответа.

## Роли

- Кирилл (капитан): ставит задачи, принимает решения, проверяет результат.
- Архитектор (Claude в чате проекта): пишет задания и проверяет результат.
- Ты (Claude Code): исполнитель, пишешь весь код в этом репозитории.

## Стек

- Next.js (App Router) + TypeScript в strict-режиме.
- PostgreSQL + Prisma.
- Tailwind CSS.
- Docker Compose: локально база данных, на сервере всё приложение.
- Playwright: e2e-тесты и автоскриншоты. Vitest: unit-тесты.
- Хостинг: виртуальная машина в Yandex Cloud, деплой через GitHub Actions (отдельное задание).

Версии бери актуальные стабильные на момент установки, фиксируй точно (без `^` и `~`). Список версий записывай в PROCESS.md.

## Структура папок

```
src/
  app/
    (public)/login/        вход
    (student)/             экраны студента S1–S9
    (staff)/staff/         экраны сотрудника E1–E4
    api/                   только то, что нельзя сделать Server Actions (health, файлы)
  server/

    auth/                  пароли, сессии, guards (requireStudent, requireStaff)

```

## Безопасность

Нарушение любого пункта означает, что задача не выполнена.

1. Проверка доступа только на сервере. Каждая страница, Server Action и route handler сначала получает сессию из cookie и вызывает guard (`requireStudent()` или `requireStaff()`).
2. Prisma вызывается только в `src/server/dal`. Функции DAL принимают `actor` из сессии и всегда фильтруют по владельцу: студент видит только записи со своим `studentId`, сотрудник только заявки своего подразделения.
   Исключения (решение Кирилла от 10.11): импорт только типов (`import type`) из `@/generated/prisma` в любом месте `src/`; Prisma в `e2e/helpers/db.ts` для ID демо-записей и очистки попыток входа в тестах; `disconnectDb` из `@/server/db` в скриптах `scripts/`, которые должны завершиться. Функции DAL без `actor` допустимы только для входа и сессий (`src/server/dal/auth.ts`) и сброса демо-данных (`src/server/dal/demo/`).
3. Никогда не принимай `studentId`, `userId`, `unitId` или роль от клиента. Они берутся только из сессии.
4. Чужая или несуществующая запись даёт `notFound()` (404), а не 403, чтобы не подтверждать существование записи.
5. Пароли хэшируются argon2id. Пароли, токены и содержимое cookie никогда не попадают в логи.
6. Сессия: случайный токен 32 байта, в базе хранится только SHA-256 от токена. Cookie: `httpOnly`, `Secure` в production, `SameSite=Lax`, `Path=/`, срок действия ограничен.
7. Вход: одно и то же сообщение при неверном логине и неверном пароле; ограничение попыток (не больше 5 неудачных за 15 минут на логин).
8. Все входные данные валидируются zod на сервере.
9. Секреты только в `.env` (он в `.gitignore`). В репозитории лежит `.env.example` без значений. Никаких секретов в переменных с префиксом `NEXT_PUBLIC_`.
10. Никаких внешних запросов в рантайме: шрифты и иконки self-hosted, без CDN. Жюри открывает сайт из России без VPN. Никаких вызовов ИИ-API в рантайме.
11. Заголовки: базовый Content-Security-Policy, `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`.
12. Любое изменение, которое затрагивает доступ к данным, сопровождается e2e-тестом в `e2e/security/`: студент A пытается открыть данные студента B, студент открывает страницы сотрудника, сотрудник одного подразделения открывает заявку другого. Везде ожидается отказ.

## Нормы и тексты о правилах

- Любое утверждение о правилах вуза в интерфейсе ссылается на код из реестра (например, N-09) и раскрывает дословную цитату. Все ссылки ведут на экран S8 «Почему так».
- Если нормы нет в реестре, не придумывай её. Пиши пометку «так устроено в прототипе» и сообщи об этом в отчёте.
- Тексты правил и цитаты хранятся в данных (таблицы `Rule`, `Norm`), а не в JSX.
- Сроки в рабочих днях считаются по производственному календарю (таблица `Holiday`). Срок «Не смогу прийти»: 3 рабочих дня ПОСЛЕ даты экзамена или пересдачи (N-04, N-16), текст «Сообщите до [дата]».

## Данные

- Только вымышленные ФИО, группы, оценки и логины. Не используй имена реальных студентов и сотрудников МГПУ, в том числе из открытых источников.
- Номера кабинетов подразделений не указываем ни реальные, ни вымышленные. Аудитории в расписании вымышленные.
- Даты в сиде задаются относительно «сегодня» по Москве. Ночной сброс демо-данных в 04:00 МСК.
- Отображение дат и времени всегда в `Europe/Moscow`, формат «18 ноября», «10:10».

## Интерфейс

- Mobile-first: всё работает от 360 px без горизонтального скролла. Проверяй в 360 и 1440 px.
- На каждой странице постоянная плашка с точным текстом: «Концепт для конкурса MGIMO AI Challenge 2026. Не официальный сервис МГПУ. Все данные вымышленные. Демо-данные обновляются каждую ночь.»
- Логотип только собственный. Официальный логотип МГПУ и его элементы не используем.
- У каждого экрана продуманы пустое состояние, загрузка и ошибка.
- Доступность: семантическая разметка, контраст не ниже WCAG AA, видимый фокус, подписи у иконок-кнопок, зона нажатия не меньше 44×44 px.
- Язык интерфейса русский.
- Лицензии зависимостей, шрифтов и иконок: только MIT, Apache-2.0, BSD, ISC, OFL. Перед добавлением зависимости проверь лицензию и допиши её в `docs/licenses.md`.

## Стиль кода

- TypeScript strict, без `any`. ESLint и Prettier без ошибок.
- Имена в коде на английском, тексты интерфейса на русском, комментарии на русском и только там, где они объясняют «почему».
- По умолчанию серверные компоненты. Клиентские только там, где нужна интерактивность.
- Мутации через Server Actions, проверка сессии внутри каждого action.
- Бизнес-правила (рабочие дни, лента действий, этапы долга, сроки этапов заявки) реализуются чистыми функциями в `src/server/rules` и покрываются unit-тестами.
- Коммиты маленькие и осмысленные, на русском, формат «область: что сделано». Не коммить `.env`, дампы базы и файлы с реальными персональными данными.

## Процесс

Описание процесса оценивается жюри наравне с кодом.

- После каждой завершённой задачи добавляй запись в `PROCESS.md` по шаблону из этого файла: дата, задача, что сделано, что пошло не так и как исправлено.
- Промпты Кирилла дословно пишет хук в `docs/process/prompts.md`. Не редактируй этот файл вручную.
- Скриншоты: `npm run screenshots` сохраняет все экраны в 360 и 1440 px в `docs/process/screenshots/<дата_время>/`.
- Если ты ошибся и исправил ошибку, опиши это честно: что было не так, как заметили, как исправили. Не скрывай ошибки.
- Субагенты из `.claude/agents/`: после каждой фичи вызывай `security-reviewer`, после текстов о правилах `norms-checker`, после UI `ui-reviewer`. Их замечания кратко фиксируй в PROCESS.md вместе с тем, что исправлено.
- Каждое задание заканчивается коммитом, в который входит docs/process/prompts.md: облачная сессия временная, незакоммиченные промпты пропадут.
- Каждое задание оформляется отдельным PR в main с описанием: что сделано, как проверить, что осталось открытым. Если все проверки зелёные, Claude Code сам вливает PR способом merge commit. Если проверки красные или нет прав, PR не вливается, Кирилл получает объяснение.
- После каждого задания обновляй docs/submission/ (см. раздел «Пакет для жюри»).

## Пакет для жюри

`docs/submission/` собирает всё, что жюри получает по условиям конкурса. Обновляется после каждого задания: статусы в чек-листе должны отражать реальное состояние.

- `README.md`: чек-лист отправки (что, где лежит / кто готовит, статус) и открытые вопросы к Кириллу.
- `comment-draft.md`: черновик комментария к работе (ссылка, аккаунты, что посмотреть). Паролей в репозитории нет.
- `tools.md`: перечень ИИ-инструментов, IDE и сервисов, для чего и на каком этапе.
- `manual-steps.md`: этапы, сделанные людьми вручную.
- `security-plain.md`: вход, хранение данных и защита простыми словами.
- `process-outline.md`: структура PDF описания процесса со ссылками на материалы репозитория.
- `npm run submission:archive`: zip исходников с историей git, без `.env` и артефактов, с проверкой на секреты. Архив не коммитится.


## Команды

Список скриптов из `package.json` поддерживай актуальным здесь:

- `npm run db:up`: поднять PostgreSQL в Docker (ждёт healthcheck). `npm run db:down`: остановить.
- `npm run dev`: dev-сервер.
- `npm run build`, `npm run start`: сборка (с `prisma generate`) и запуск production.
- `npm run typecheck`: `prisma generate` и `tsc --noEmit`.
- `npm run lint`: ESLint без предупреждений.
- `npm run format`: Prettier, исправляет файлы. `npm run format:check`: только проверка.
- `npm run test`: unit-тесты Vitest (`src/**/*.test.ts`, `.claude/hooks/*.test.ts`).
- `npm run test:e2e`: Playwright. Без `BASE_URL` сам поднимает dev-сервер.
- `npm run screenshots`: автоскриншоты всех экранов из `e2e/screens.ts` в 360 и 1440 px. Без запущенного сервера сам поднимает `next dev`.
- `npm run db:migrate`: применить миграции (`prisma migrate deploy`). Новая миграция в разработке: `npx prisma migrate dev --name <имя>`.
- `npm run demo:reset`: удалить все данные и засеять демо заново (даты от «сегодня» по Москве). Нужны `DEMO_PASSWORD_*` в `.env`. Это же `prisma db seed`.
- `npm run submission:archive`: zip исходников с историей git для жюри в `dist-submission/` с проверкой на секреты.
- `postinstall`: `prisma generate` после `npm install`.

## Готово означает

- `typecheck`, `lint`, `test`, `test:e2e` проходят.
- Скриншоты сняты, если задача меняла интерфейс.
- Запись в PROCESS.md добавлена.
- Изменения закоммичены.
